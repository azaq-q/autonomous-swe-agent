# Autonomous SWE Agent 简历项目实现指南（面向字节跳动等顶级公司）

> 目标：把「Autonomous SWE Agent」做成一个**经得起技术面试深挖**的简历项目，而不是「调 API 拼装的 demo」。
>
> 关联文档：[产品设计](./autonomous-swe-agent.md) · [实现路线对比](./implementation-routes.md)

## 1. 顶级公司面试官到底看什么

投递字节等公司的 AI/后端岗位时，简历项目会被追问以下问题：

| 关注点 | 面试官会问 | 你的项目必须能答 |
| --- | --- | --- |
| 技术深度 | 「你是自己写的还是调的框架？」 | 能讲清每个模块的实现与 trade-off |
| 工程能力 | 「怎么做可靠性/可扩展性？」 | 有状态机、重试、可观测、异步任务 |
| 量化结果 | 「效果怎么样？怎么证明？」 | 有 Eval/benchmark 指标，不是"看起来能用" |
| 技术难点 | 「最难的 part 是什么？」 | 有明确的技术难点与解法 |
| 思考方式 | 「为什么这样设计？」 | 能说清选型理由、备选方案、取舍 |

**核心结论：顶级公司不关心你用了多少框架，关心你是否真正解决了一个有难度的问题，并能量化、能讲透。**

## 2. 项目定位：做一个「有壁垒」的 SWE Agent

### 2.1 避免沦为 demo 的三个陷阱

1. **纯拼装**：只用 LangChain/OpenHands 把组件串起来，没有自己的核心逻辑 → 面试一问就露馅。
2. **无评测**：跑通一个例子就写进简历 → 无法证明效果，也无法迭代。
3. **面面俱到但都很浅**：Planner/Code/Test/Review 都做，但每个都只是 prompt 调 LLM → 没有深度。

### 2.2 正确的定位策略

> **做深 1~2 个核心模块 + 搭好完整闭环 + 用评测证明效果。**

建议把「深度」集中在这两个方向之一（二选一重点突破）：

- **方向 X：Agent 编排与可靠性** —— 多 Agent 状态机、错误恢复、人工审批、可观测。
- **方向 Y：代码检索与理解（RAG）** —— 大仓库语义检索、结构化解析、精度优化。

其余模块（工具、Sandbox、前端）做到「完整可用」即可。

## 3. 推荐实现路线

采用上一份文档的 **路线 B（框架编排 + 自研核心）**，并叠加 **路线 C 的深度自研** 于重点模块：

| 层次 | 做法 | 说明 |
| --- | --- | --- |
| 编排 | 自研状态机 + LangGraph 子图 | 核心逻辑自己写，框架只做图执行 |
| 检索（重点） | 自研分块 + 重排序 + 结构化解析 | 可讲、可量化 |
| Agent Loop | 自研 ReAct/Plan-Execute | 不直接依赖框架默认实现 |
| 工具 | 自研 Git/File/Terminal | 核心壁垒 |
| Sandbox | E2B 起步，后续自建 Docker 隔离 | 节省时间，聚焦核心 |
| 存储 | PostgreSQL(pgvector) + Redis | 减少组件数量 |
| 前端 | Next.js | 展示层，够用即可 |

**关键取舍：把时间花在「能讲、能测、能写出深度」的模块上，把「纯基础设施」外包给成熟组件。**

## 4. 核心模块实现要点（每个模块都讲得出难点）

### 4.1 Agent Orchestrator（编排与状态机）

**难点**：多 Agent 依赖、失败重试、长任务状态持久化。

**实现要点：**

```
状态机设计（不要只靠 LLM 自由发挥）：
  PLANNING → ANALYZING → CODING → TESTING → REVIEWING → APPROVAL → DONE
                                    ↖______失败回退______/

- 用显式状态转移表，而非 if-else 堆叠
- 每个 Agent 输出结构化 JSON（含 status / result / next_action）
- 任务状态持久化到 PostgreSQL，支持断点续跑
- 失败自动重试 + 降级（测试失败 → 回退到 Coding Agent 修）
- 人工审批节点（Human-in-the-loop）
```

**面试可讲**：状态机设计、错误恢复策略、为什么需要显式状态而非让 LLM 自由决策。

### 4.2 Repository Understanding（代码检索 RAG）

**难点**：大型仓库无法整体入上下文；语义检索精度不足。

**实现要点：**

```
Pipeline：
  源码 → tree-sitter AST 解析 → 结构化分块（按函数/类切分）
       → 元数据增强（文件路径、符号名、依赖关系）
       → Embedding → pgvector 索引
       → 查询时：向量召回 + 关键词召回 + 重排序（rerank）
       → 拼接符号依赖上下文（调用图）→ 注入 LLM

关键优化（可量化的点）：
- 用 AST 而非固定长度分块，保留语法完整性
- 混合检索（向量 + BM25 关键词）提升召回
- 基于 import/调用关系做上下文扩展
```

**面试可讲**：为什么固定长度分块不好、AST 分块的优势、混合检索与重排序如何提升命中率、用哪些指标衡量检索效果（Recall@k / 定位准确率）。

### 4.3 Tool System（工具调用）

**难点**：让 Agent 正确、安全地调用工具。

**实现要点：**

```
- 自研工具协议（统一 schema：name/description/parameters）
- Git Tool：clone/branch/commit/push/create PR
- File Tool：read/write/search/diff（diff 是关键，让 Agent 看 patch 而非整文件）
- Terminal Tool：受限命令执行（白名单 + 超时）
- 每次工具调用都落库（execution 表），可回放、可观测
```

**面试可讲**：工具 schema 设计、为什么 diff 对代码 Agent 重要、工具调用结果的上下文截断策略。

### 4.4 Sandbox 安全隔离

**难点**：Agent 生成代码有风险，需要隔离与资源限制。

**实现要点：**

```
- E2B 起步（托管隔离，快速跑通）
- 进阶：自建 Docker + gVisor/Firecracker
- 限制：CPU / Memory / Network（可关闭外网）/ 文件权限 / 超时
- 每次任务一个独立容器，结束即销毁
```

**面试可讲**：沙箱隔离级别（容器 vs 微虚拟机）、资源限制、网络策略、为何不能裸跑。

### 4.5 Evaluation（评测体系）——**这是区分 demo 与真项目的关键**

**难点**：如何证明 Agent 真的有效。

**实现要点：**

```
- 引入 SWE-bench 或自建评测集（10~30 个真实 Bug/Feature）
- 指标：任务解决率（Resolved %）、一次通过率、测试通过率
- 记录每个任务：prompt / Agent 轨迹 / patch / 是否通过
- 对比实验：不同模型、不同检索策略、不同编排策略的效果
- 输出评测报告，作为简历的量化证据
```

**简历可写**：如「在自建 20 个真实任务的评测集上，解决率达到 X%，相比 baseline 提升 Y%」。

> 量化结果是顶级公司简历的**硬通货**。没有评测的项目，面试官会直接归类为「玩具」。

## 5. 差异化亮点（让项目脱颖而出）

以下任选 1~2 个做出特色，即可与海量「SWE Agent 教程项目」拉开差距：

1. **可观测性**：Agent 每一步轨迹可视化（前端 Timeline + 后端 trace），面试时直接演示。
2. **Self-Reflection**：Agent 测试失败后自动反思并重试修复（结合 4.1 的回退机制）。
3. **多模型路由**：复杂推理用大模型，代码总结/分类用小模型，展示成本意识。
4. **成本统计**：每个任务的 token 消耗、费用、耗时统计，展示工程化思维。
5. **人工反馈闭环**：Accept/Reject/Modify 反馈用于优化后续任务。

## 6. 里程碑规划

| 里程碑 | 交付物 | 验证方式 |
| --- | --- | --- |
| M1 | 单 Agent 闭环：改文件 → 跑测试 | 一个真实 repo 上跑通 |
| M2 | 工具 + Sandbox + 状态机 | 完成「改代码 → 测试 → 修」循环 |
| M3 | 多 Agent 编排（Planner/Code/Test/Review） | 一个 Bug 修复任务完整走通 |
| M4 | RAG 检索 + Memory | 检索命中率评测 |
| M5 | 评测集 + 量化报告 | 20+ 任务解决率指标 |
| M6 | Web UI + 可观测 + PR 创建 | 端到端演示 |

## 7. 简历描述（可直接使用）

### 项目标题

**Autonomous SWE Agent — AI 软件工程智能体**

### Resume Bullets

- 设计并实现自主软件工程 Agent，支持 GitHub 仓库分析、代码补丁生成、Docker 沙箱测试与 PR 创建，通过多 Agent 编排完成完整闭环。
- 基于 LangGraph 构建 Planner/Coding/Testing/Review 多 Agent 工作流，实现显式状态机、失败重试与人工审批（Human-in-the-loop）。
- 自研代码理解 RAG 管线：tree-sitter AST 分块 + 混合检索（向量 + BM25）+ 重排序，在大规模仓库上提升语义检索精度。
- 搭建自建评测集（N 个真实任务），任务解决率达 X%，并通过多模型路由与资源限制控制成本。

### 技术栈标签

`LangGraph` `FastAPI` `PostgreSQL(pgvector)` `Redis` `Docker/E2B` `Next.js` `OpenAI/Claude API` `tree-sitter`

## 8. 面试高频追问与准备方向

| 追问 | 准备方向 |
| --- | --- |
| 为什么不用现成 OpenHands？ | 讲差异化：自研编排/检索/评测，可控性 |
| Agent 失败怎么恢复？ | 状态机、重试、回退、断点续跑 |
| RAG 怎么提升精度？ | AST 分块、混合检索、重排序、指标 |
| 怎么保证沙箱安全？ | 隔离级别、资源限制、网络策略 |
| 效果怎么证明？ | 评测集、解决率、baseline 对比 |
| 最难的 part？ | 提前准备好 2~3 个技术难点 + trade-off |
| 成本怎么控制？ | 多模型路由、token 统计、上下文截断 |
| 多 Agent 怎么协作？ | 状态传递、依赖、结构化输出 |

## 9. 避坑清单

- ❌ 只跑通一个 demo 就写「已完成」，没有评测与指标。
- ❌ 每个 Agent 都只是「写一段 prompt 调 LLM」，没有状态机与工程约束。
- ❌ 堆砌技术名词（Temporal、Milvus、Kafka）却讲不出为什么需要。
- ❌ Sandbox 用 `subprocess` 裸跑，安全问题被一问即穿。
- ❌ 简历写「用了 LangGraph」却讲不清它的作用与替代方案。
- ✅ 把 1~2 个模块做到能写博客、能答辩的深度。
- ✅ 保留完整评测数据与轨迹，面试时可演示可复现。
